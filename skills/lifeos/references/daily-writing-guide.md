# Daily 写作规范与对照样张

## 核心原则

日报是写给**一个月后的自己**看的：忘了当天细节后，翻开这一页能立刻找回两样东西——**今天做成了什么（世界变成了什么样、现在能拿它干什么）**，以及**促成或推翻它的判断（为什么这么定、哪里判断错了）**。

- **判断只有两种合法来源**：① 本人亲口说出的原话（对话、补录、随记或聊天里的拍板、后悔、「当时以为」「早该」）；② 可核验的事实对照（后来的结果推翻了先前决定、违背了既有约定、或离里程碑的距离变化）。写作者自己脑补的「进展顺利」「效率很高」「结构应该从使用出发」一句不写。
- **证据退场**：会话、命令、测试和核对过程用来帮你判断「今天到底做到哪」，判断完了就退场。只证明某件事查过、测过、核对过的句子全删。
- **第一人称视角**：用「我决定」「我推翻了」「我原以为」写判断与纠偏；动作和结果可省略主语直接起笔；涉及他人动作时点名区分。

## 三把价值标尺与状态增量公式

不同项目角色下，「有价值的变化」判据不同（具体职责以 `agent-profile.md` 和本人最新说明为准）：

- **亲自实现（Builder）**：看**解锁了什么以前不能用的能力**，或**用真实数据/场景验证（推翻）了什么假设**。改样式、修零碎 Bug、配置环境、重复跑测试，除非改变了可用边界或暴露新风险，否则全部并进所属方向的一句结果里。
- **产品 / 项目负责（PO / PM）**：禁用「对齐了口径」「跟进了进度」「开了评审会」这类零信息词。必须落到三选一：**① 敲定了什么边界或规则（定成什么、排除了什么）**；**② 消除了什么阻塞（谁接走了什么交付物、承诺了什么节点）**；**③ 暴露了什么新矛盾（原方案哪里走不通）**。
- **状态增量自检公式**（进「核心主线」必须填满前 3 槽）：
  `昨天为止的旧状态/卡点 → 今天之后的新状态/可用能力 → 靠我哪次关键取舍或事实反馈促成 → 眼下还卡在哪一步`

## 三层准入

1. **核心主线（最多 3 条）**：当天投入最大、本人明确推进、或发生过推翻与重定位的工作（没做完但投入最大也入选）。按实际交付对象和共同目标划分，不按仓库、对话或文件数机械分组。
2. **还做了（最多 10 条，每条一行）**：改变了某个对象状态、日后可能需要回头查的事（发给谁什么材料、收到谁什么答复、定了什么小口径）。同一件事不与主线重复。
3. **不进正文**：本机维护、依赖升级、查资料、格式清理、同步副本、日报草稿操作，以及提交/分支/Tag/测试通过/发布动作本身（这些由 frontmatter 计数与 ID 承担）。

## 固定骨架

内容不成立的章节**整节省略**，不为版式凑数；篇幅上限常规日 2,000 字、重大转折日 3,500 字。

```markdown
# 当日概览

三句以内：先点今天最要紧的一件和它为什么要紧，再说总体到了哪一步。不预告后文章节。

## <核心主线一句话标题，写做成了什么>

**一句加粗结论：先说清做成了什么，再带出最有分量的那个决定或转折。** 随后一段 200 字以内（多轮纠偏可到 300 字），写促成它的决定与理由（本人原话优先），以及仍会影响下一步的现实缺口。多方向变化可用两三个短要点，每条只写结果。

## 还做了

- 一行一条，最多十条，写清对象和终态。

## 会议

- 起止时间 名称 — 服务的项目或需求（部门例会、培训写性质；可加简短结果如「— 拍板……」「— 无结论」）
共 N 小时。

## 想明白的

只收两种：① 当天出现的认知落差（原以为/原做法被事实推翻且当天弄清了根因与避坑法）；② 本人当天亲口说出的道理。每条一段，先给认识本身，再点明出自当天哪件事。大多数日子没有，整节省略。
```

**禁写清单**：正文绝不出现任何 ID（`ACT-` / `TASK-` / `EVT-` 等）、40 位或短 SHA、行号、本机绝对路径（`/Users/...`）、流水线阶段名（`local test passed` / `gate` / `commit` / `tag`）、审计计数散文，以及无判断意义的数量（改了几个文件、发了几条消息、截了几张图）。交付层级用世界里的现实状态表达，例如：「Demo 已发研发群，本地又改了一轮还没重发」「新逻辑已合并，还没碰过真实报价数据」。

## 写入前 10 项自检（全部为 Yes 再写）

1. 只看 `# 当日概览` 和各主线的加粗首句，一个月后的自己能不能复述今天做成了什么、有没有拍错板？
2. 每条核心主线是否不超过 3 条，且能套进「旧状态 → 新状态 → 关键判断 → 现实缺口」？
3. 延续中的主线是否只写了今天的增量，没有重复昨天日报已说清的背景？
4. 所有写进正文的判断、理由、反思，是否都能对应到本人原话或可核验事实，没有写作者的自我感慨？
5. 「还做了」是否每条一行、写清对象和终态、总数不超过 10 条，且未与核心主线重复？
6. 是否已经彻底删除「待办与依赖」「需要关注」两节（持续跟进转交 Work 候选）？
7. 「想明白的」是否确实出自当天的认知落差或本人亲口原话，而不是泛泛的通用道理（否则整节省略）？
8. 正文是否零 ID（`ACT-` / `TASK-` / `EVT-` 等）、零 SHA、零本机路径、零阶段名、零无判断意义的数字？
9. 交付层级是否只按现实可用状态说清（谁能用、什么还是旧的、什么没碰过真数据），未跨层推断？
10. 「会议」一节是否仅包含本人确认过的会议（未启用或未确认前不写入）？
