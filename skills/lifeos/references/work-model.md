# 工作模型参考

进入任何记录、修改、完成、排期、划掉、转化或回答分支前读取本文件。`lifeos` 的 Work 路由负责授权与执行顺序；本文件负责选哪种记法、状态语义和幂等规则。

## 选哪种记法

Work 按天记下的每一笔只有四种，外加项目引用和实体名词：

- **`•` 待办（task）：** 定了要做、结果可验证的事。定没定是本人的判断，不从「应该」「可以考虑」推出来。等别人交付的事也记成待办，负责人写对方。
- **`–` 随记（note）：** 随手想到的点子、要记住的事，还没决定做。不虚构负责人、日期或星标。
- **`?` 疑问（question）：** 要查、要问或要拍板的问题。一件事「要不要做」没定时也记成疑问。
- **`!` 洞见（insight）：** 本人认过有用的一句判断，`--context` 必须写来由（让他想明白的那件具体的事，1–3 句）。只有本人说「这条留下」或确认了周期报里的候选才写；日报「想明白的」是 Agent 起草的，不直接当洞见。

一件事在项目里有阶段、里程碑，由项目 CURRENT 和规划文档负责；Work 不保存阶段。需要表达「这个阶段 10 月 14 日前完成」时，就是一条带截止时间的待办。

## 每一笔的字段

| 字段 | 含义 |
|---|---|
| `id` | 前缀看类型：`TASK` / `NOTE` / `ASK` / `INS`，后接日期与序号 |
| `text` | 正文：一句话。待办写要做成的结果，读完就能判断做没做完；完成标准是多项清单时，写它们合起来达成的那个结果，清单留在项目文档。疑问写要回答的问题，随记写要记住的想法，洞见写已认可的判断。不写做法和理由 |
| `project` | 挂在哪个已跟踪项目上（`project_key`），可以不挂 |
| `status` | 当前状态，见下表 |
| `note` | 进展：这一笔现在怎样，只留最新一句；待办记下时已有现状，用 `task-add --note` 一起写。还在账上时写卡在哪、下一步在谁手上、预计什么时候；了结时写完成了什么、划掉或退役原因、疑问答案、推后原因；洞见写写进了哪里 |
| `ref` | 当前状态指向的另一笔：转成了哪一笔、答案来自哪条洞见、被哪条洞见取代 |
| `context` | 背景：只放读正文还缺的那一句（为什么在我账上，或正文里的说法指什么）和一个详情入口（项目文档标题、在线链接或工作区相对路径），都不需要就留空；记下时写定，之后只修错误或失效的入口。洞见必填，写形成判断的具体来由，1–3 句 |
| `created_at` / `updated_at` | 什么时候记下（也决定记在哪天）、最后一次变化 |
| `starred` | 待办与疑问：重要 |
| `owner` | 待办：负责人，空表示本人，写了名字就进「等别人」 |
| `due` / `month` | 待办：结果的硬截止；排到以后时排到哪个月 |

来源（`--source`）只写进审计事件，不存进记录。正文、背景、进展、项目、负责人和星标每次改动的前后值，以及每次状态变化，都由 CLI 自动记进审计事件，`lifeos work show ID` 按时间列出；这就是一笔的完整过程。

## 字段写法与信息去向

按什么时候写来分：背景记下时写定；同一个结果换说法或收放范围时改正文，ID 沿用；进展随时覆盖。要做成的变成另一件事时——原来那件做完了、不做了或并进了别的待办——原来那笔按实际完成或划掉，进展写明去向，新结果另记一条；背景不记合并和改名经过。

来源材料里的信息各有一个去处：完成标准收成正文那一句结果，现状和下一步写进展，硬截止写 `due`，以后再做的月份写 `month`；详细排期、执行步骤、多人分工、完整验收清单与过程证据留在项目文档，由背景里的详情入口指过去。

过程不手写：不在背景或进展里追加「某日：……」这类流水，也不为留底把旧内容挪进别的字段；覆盖之后，旧的一句由审计事件保存。预测或不确定的日期写进进展。本人要求补上更早的进展时，依据已确认日报等证据逐版补记：`entry-backfill ID --as-of <证据当天> --note "当时那一句"`，`--source` 写证据出处；补记不改当前进展，现状变了另用 `entry-update`。

进展在本人确认了变化，或关注联动带来「卡在哪、下一步在谁手上、预计时间」的变化时覆盖一句；结果、截止或状态变了，用对应命令。日报「欠与等」逐日承接当天欠谁什么、等谁什么，不需要每天同步到进展。

没有项目文档时，背景可以多一句执行提示；成段的参考资料放到它自己的落点，背景只留链接或位置。只有已确认要做、有人认领、需要独立跟踪的动作，才按授权另记待办。

## 状态

| 记法 | 状态（CLI 值 → 叫法） | 用哪个命令 |
|---|---|---|
| 待办 | `open` 待做 · `scheduled` 排到以后 `<` · `done` 完成 `✓` · `dropped` 划掉 | `task-done --note`、`task-schedule --month`、`entry-drop --note`；排到以后的用 `entry-update --reopen` 取回 |
| 随记 | `open` 记着 · `converted` 转成别的 `>` · `dropped` 划掉 | 转化用新一笔 add 命令的 `--from`；`entry-drop --note` |
| 疑问 | `open` 没想通 · `done` 想通了 `✓` · `converted` 转成别的 `>` · `dropped` 划掉 | `question-answer --note [--by INS]`，或 `insight-add --answers`；`--from`；`entry-drop` |
| 洞见 | `open` 有效 · `dropped` 退役 | 写成规则后 `entry-update --note "写进了哪里"`；被推翻或不再成立用 `entry-drop --note [--by 新洞见]` |

- **必须写进展（`note`）的：** 待办完成或划掉、随记划掉、疑问想通或划掉、洞见退役。
- **截止时间：** `due` 只表示结果的硬截止，过了才算逾期；7 天内到期算紧急。改期用 `task-reschedule`，推迟或清除必须带原因码；输入纠错用 `date_correction`。预测或不确定的日期写进进展，不写 `due`。
- **星标：** 只用于待办和疑问，表示本人认为重要。Agent 不替本人判断重要与否；本人没说就不标星。
- **负责人：** 本人负责时不传 `--owner`。别人负责时写已确认的真实名字；缺失时不猜。已确认的实体改名用 `term-update`，会同步负责人写着旧名字的待办。
- **等别人：** 不是状态。自己的事卡在别人手上时，另记一条负责人是对方的待办（例如「凯健提供每小时热榜推送」），自己那条保持待做，或排到以后。

## 月初盘点

每月初跑 `lifeos work brief --mode monthly`，它列出三类：排到的月份已到的待办、超过 30 天没有变化的待办/随记/疑问，以及本月还没动过的星标。逐笔问本人去向，按回答执行：继续（`entry-keep`）、排到以后（`task-schedule`）、划掉（`entry-drop`）、转成别的一笔（add 命令加 `--from`），或者去掉星标（`entry-update --unstar`）。本人没给去向的保持原样，不替他选。

## 稳定幂等

幂等键标识「这一次确认的写入」，让重试不重复写；同一件事有没有在别的会话里记过，由查重负责。来源有不可变 ID（日报候选、DChat 消息、已有记录 ID）时，用它和记法派生；没有时（如 CURRENT 推进项），用本次会话 ID、记法和本次确认中的序号。不使用时间、随机数或可变展示文字。同一次重试复用同一个键，写入内容变了就换新键；同一个键碰上不同内容时 CLI 会报错，先回读核对是重试还是另一条写入。调用方提供已经确认的措辞与来源身份，`lifeos` Work 分支统一负责生成键和处理重复项。

## 证据与范围

不得从建议、日报候选或周边项目语境推断负责人、日期、星标、原因、完成状态或归属。项目正式状态、代码、部署和外部沟通不进入 Work 账本。

完成标准：已确认的事实足以支持所选记法和状态；必填进展完整，背景里没有进展或日期流水；调用公共 CLI 写入前已经应用稳定幂等规则。
