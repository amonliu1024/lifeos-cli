# 工作模型参考

进入任何创建、更新、完成、取消、归档或改期分支前读取本文件。`lifeos` 的 Work 路由负责授权与执行顺序；本文件负责对象选择、生命周期语义和幂等规则。

## 对象选择

- **待办（Task）：** 一个由真实责任方负责、结果可验证的动作；适用于一次行动或一个可闭环结果。
- **轻事项（Light work item）：** 一条持续工作主线，有简洁的下一门槛，通常包含 0–2 个待办，但没有可独立验证的阶段链。
- **路线事项（Route work item）：** 仅用于存在多个可独立验证阶段的工作。它必须有且只有一个 `current` 里程碑；未来里程碑保持 `planned`，未完成待办挂在当前里程碑下。
- **闪念（Idea）：** 尚未承诺的想法；保留在 `inbox`，不虚构责任方、日期或价值。只有已经确认待办或事项后才完成提升。
- **成果胶囊（Achievement）：** 只关联已完成待办的可复用结果，包含结构化证据；适用时保留归档或替换原因。

## 生命周期与字段

- 待办必须有可验证结果和责任方。`next_action` 是当前下一步文字；`due_at` 只表示结果的硬截止。真实开始日期保存在 `task_started` 审计事件中，并由视图派生；不得根据创建时间、更新时间或改期历史推断。只有已经观察到时才补充 `why`、`completion_criteria` 或 `context`。
- `responsible_party.kind=self` 始终解析为规范的 `ENT-SELF` 名称和实体 ID，不提供或保留昵称。人读视图省略本人，只显示明确的个人或组织名称，不推断缺失责任方。已确认的实体改名使用通用 `term-update`，并级联更新引用同一 `entity_id` 的待办名称。
- 改期必须记录明确原因类别。推迟或清空硬截止需要用户提供原因；输入纠错使用 `date_correction`。变更后回读日程历史。
- `waiting`、`paused` 和 `cancelled` 保留 `status_reason`。完成通过 close 流程写入摘要、完成来源、价值和反思；没有实现价值时也要明确记录。
- 路线里程碑的状态为 `planned`、`current`、`completed` 或 `cancelled`。完成时记录摘要、完成来源和决定；继续或调整时激活下一个 planned 里程碑，暂停或关闭时把原因传递给父事项。

## `next_gate` 写法

`next_gate` 用一句话回答：事项进入下一阶段或关闭之前，必须跨过什么门槛。只写一个可观察结果或决定，使用“完成……并形成……”或“确认……”等结果句式，保持单行，通常不超过 30 个中文字符。

需要机器语义的日期写入里程碑 `target_at` 或待办 `due_at`。简单的个人行动计划可以在 `next_action.text` 前使用六位日期短前缀，例如 `260825开始梳理……`；文字保持自然简短。该前缀只是普通文本：不得解析、排序、过滤，不得用于提醒或逾期判断，也不得写入日程历史。背景、责任、原因、长条件链和任务清单分别写入对应字段或关联待办。没有计划日期时，`next_action` 只保留行动文字。

路线事项的根 `next_gate` 保持为空，当前里程碑的 `outcome` 遵循相同的单行规则。brief 渲染器不会截断或概括不合规的门槛文字。

## 稳定幂等

幂等键从稳定事实源、对象类型和不可变来源身份派生，不使用时间、随机数或可变展示文字。同一次重试复用同一个键；只有真实来源事实不同才使用新键。调用方提供已经确认的措辞与来源身份，`lifeos` Work 分支统一负责生成键和处理重复项。

## 证据与范围

不得从建议、日报候选或周边项目语境推断责任、日期、价值、原因、完成状态或归属。项目正式状态、代码、部署和外部沟通不进入 Work 账本。

完成标准：已确认事实足以支持所选对象和生命周期；必填状态与原因字段完整；调用公共 CLI 写入前已经应用稳定幂等规则。
