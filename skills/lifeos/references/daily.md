# Daily 工作流

一天一份事实性日报，写进 Private Runtime，由本人确认。目标是恢复当天真实工作主线及其终态，不是逐条转述 Activity，也不要求每天都有价值、踩坑或经验。Git 提交和 DChat 是可选的辅助证据，不替代 Agent 会话、Work 或本人补录，也不能单独定义当天是否工作。读取来源证据不产生 Work 写入授权，确认日报也不等于确认 Work。

本文件拥有流程顺序、主线判断和正文表达。证据语义、采集门细则、计数口径和结论强度由 [`session-evidence.md`](session-evidence.md) 拥有，DChat 采集与项目确认由 [`dchat-evidence.md`](dchat-evidence.md) 拥有；这里只写触发条件和它们如何改变当前动作。

## 一、取得窗口

```bash
lifeos reports path --day <YYYY-MM-DD> --json
lifeos reports begin --day <YYYY-MM-DD> --json
```

目标日默认今天。先用只读的 `path` 取得状态和唯一自然日窗口；日报尚未确认、需要建立或覆盖 draft 时再执行 `begin`，并核对两者返回的 `window.from` / `window.to` 完全一致。已确认日报保持不变；本人只要求重新采集证据时，直接使用 `path` 返回的窗口，不调用 `begin`，也不自行做日期运算。只有本人明确要求重做日报时才使用 `begin --redo`。

完成标准：目标状态和唯一自然日窗口已取得；重做时旧快照已由 CLI 留存。

## 二、盘点并审计证据

读取正文、判断 Activity、处理生命周期或填写 frontmatter 前，先读 `session-evidence.md`，本节的采集门、完整性判据、异常审计清单和计数口径全部按该文件执行。运行 `lifeos dchat validate --json` 判断独立 DChat Evidence 是否已配置；配置有效时再读 `dchat-evidence.md`。尚未配置只表示这一路尚未启用，不阻塞其他来源形成日报。

```bash
lifeos sessions scans --from <window.from> --to <window.to> --json
lifeos project discover --json
lifeos project validate --all --json
lifeos sessions validate --scan <scan-id>
lifeos sessions scan --source all --from <window.from> --to <window.to> --json
lifeos sessions index --from <window.from> --to <window.to> --json
lifeos work changes --from <window.from> --to <window.to> --json
lifeos git scans --from <window.from> --to <window.to> --json
lifeos git scan --from <window.from> --to <window.to> --json
lifeos git validate --scan <git-scan-id> --json
lifeos dchat validate --json
lifeos dchat scans --from <window.from> --to <window.to> --json
lifeos dchat scan --from <window.from> --to <window.to> --json
lifeos dchat index --from <window.from> --to <window.to> --json
```

按以下顺序执行：

1. 先运行完整 `project discover` 与 `project validate --all`，记录当前发现根、有效项目和 findings。新合法清单无需 Work 跟踪即可参与项目映射；单个非法或冲突项目只影响该项目，但如果可能改变日报主线归属则保留 Pending。
2. 过 Sessions 采集门：查目标窗口的 `sessions scans`，按 `session-evidence.md` 判断能否复用并校验选中的 `scan_id`，否则执行一次精确窗口的 `sessions scan --source all` 再校验。随后读取无过滤的完整 index，并完成其中的异常审计。来源不可读、校验失败，或覆盖与异常不足以支撑结论时，停止定稿并报告具体 Pending；不要把空 index 写成“昨日没有工作”。
3. 读取窗口内全部 Work changes。它们证明 LifeOS 账本发生了什么变化，不自动证明对应项目已经交付。
4. 有显式注册的 Git 仓库时必须执行 Git 检查门：先读目标窗口的 `git scans`，可复用快照须通过 `git validate --scan`，否则按需运行一次 `git scan`。Git scan 只读本地提交历史、写入私有证据快照，不修改仓库、不访问 remote、不写 Work。Git 不可用、没有注册仓库或扫描失败，不自动等于当天没有工作；只有当日报结论依赖 Git 且缺口影响事实时，才披露 Pending 或提问。正文出现任何提交、推送、部署层级断言时，对应仓库窗口内必须有通过校验的快照，否则该断言降级为“会话陈述”。
5. 本人主动提供的补录作为第三路证据；没有实质缺口时不为了凑齐输入而提问。
6. DChat 已配置时，按 `dchat-evidence.md` 通过精确窗口 scan 和 validate 后读取完整 index，只对可能改变工作主线的会话渐进调用 pack。可读 scope 只采用 DChat 的结构化会话类型与当前项目清单中的群 VID，不按账号名称、头像或消息内容猜测身份，也不用群名、活跃度、本人是否发言或关键词扩大范围。

完成标准：Sessions 采集门与完整 index 已通过 `session-evidence.md` 的判据；所有可能改变自然日事实的异常已有解释或 Pending；Work changes 已读取；Git 检查门已执行且失败与缺失边界已解释；DChat 已配置时其采集门与项目清单冲突已处理，未配置时没有把缺失解释成“没有聊天工作”。

## 三、建立工作主线

先选主线，再选需要深读的 Activity。Activity 是 evidence activity，不是任务、项目或日报章节；允许把多个来源、并行子 Agent 或多个 `project_key` 的 Activity 合并成同一工作主线，也允许把目标发生变化的长 Activity 拆成不同阶段。

工作主线以共同目标和可共享的总体终态为边界，不以项目名、仓库、对话或修改文件数机械分组。同一项目内目标和闭环状态彼此独立的工作可以拆成不同主线；不同项目只有在任务正文或交付证据明确表明它们共同服务于同一交付对象，且能够共享一个不冒充任一项目的总体终态时才合并。部门、主题、工具、群聊或名称相近不构成共同目标。

按以下信息判断重要性：

- 本人当天明确要推进的目标；
- 真实能力、交付状态或项目判断发生的变化；
- 反复纠偏、被推翻的判断或关键决策；
- 验证结果、实质风险、未闭环边界；
- 与当前项目主线的关系。

Activity 数量、`signal_score` 和 `project_key` 只提供线索。投入强度不能独自证明价值或完成，但它是重心的直接证据：当天投入最大、或经历过反复推翻与重新定位的工作，即使仍在进行中也必须作为核心主线出现，不因“还没做完”降入其他进展。反过来，机制性、顺手完成且不改变可用能力、判断或授权边界的动作（例行同步、格式校正、重复执行的检查）不单独成句，必要时并入所属主线一笔带过。为每个高重要性 Activity 标记 `纳入某主线 / 并入其他 Activity / 次要概括 / 省略及理由`，避免重要活动静默消失。

主线数量、层级和章节顺序全部由当天事实决定：一项工作明显主导当天时提升为唯一核心主线，其他事项降入“其他进展”；多项工作确有相近叙事权重时才并列；没有足够重要的工作时可以不设核心主线。整个流程都不为版式凑数——空章节直接省略，内容不成立时不补写。

### 项目边界审计

`project_key` 不能单独决定业务主题，它与 `workspace`、`changed_targets` 共同构成边界证据；DChat 会话候选只限定搜索范围，不覆盖已核验 Activity 的归属。

写初稿前，为每条拟定主线回看这三项与任务对象：标题含具体项目名时，纳入内容必须属于该项目或确有证据属于该项目交付；不同项目只是主题相近、没有共同交付对象时立即拆分。确需跨项目合并时使用中性标题，分别说明各项目贡献与边界。

### 变化结构

为每条主线判断变化结构。它同时决定深读到哪和正文写成什么形态，不作为正文固定标签：

- **简单变化**：围绕一个对象形成单一结果，没有影响终态的分支或转折。读到结果和边界即可，写成一个短自然段。
- **多方向变化**：同一目标下有多个可分别说明的能力、规则、材料、运行或协调变化。按真实对象或结果归并，写成总体结论加按方向归并的短要点，不给每个方向重复填写问题、纠偏、结果和边界。
- **多轮变化**：同一方向经过验证、反馈或纠偏，后续判断实质替代了早期判断。只深读实质改变最终方案、完成状态、风险或下一步的关键转折；先写最新结论，只在理解最终判断确有需要时补充少量转折，普通尝试和已被后续结果覆盖的中间状态压缩或省略。
- **混合变化**：同时存在多个方向，且只有其中部分方向发生多轮变化。先按方向拆分，只展开发生关键纠偏或存在独立风险的方向；方向本身足够复杂、具有独立终态时才使用局部小标题。

只有变化会改变可用能力、项目判断、责任边界、交付状态、实质风险或下一步时，才把它作为独立方向。多个文件修改、参数调整、重复测试或普通措辞迭代不因此独立成项。

完成标准：当天所有高重要性 Activity 都有去向；并行分支已归并，混合目标已拆开；每条核心主线的变化结构已确定；项目边界审计没有发现被单一项目标题吞并的异项目工作；主线层级反映当天真实重心。

## 四、渐进深读与终态收敛

按 `session-evidence.md` 的渐进深读执行：核心主线读全部相关 Activity 的 `pack --activity`，承载关键终态、验证或冲突的 Slice 再用 `show` 回查；次要进展读到目标、动作、结果和边界成立即停；琐碎活动留在 index 粒度。partial 和 `interrupted_with_result` 只在承载被引用事实或可能改变终态时深读。

每条核心主线先收敛最新结论，再按已确定的变化结构整理支撑它的内容。需要保留多轮演变时，按 `最新结论 → 关键转折及原因 → 证明力最强的最新证据 → 剩余边界` 组织；没有纠偏时不补造转折。终态优先级取决于证据能证明什么，而不是哪句话最肯定。

交付层级按 `session-evidence.md` 的链条分别记录，前一层不能推出后一层；Git 提交只能证明对应仓库在该窗口产生了 commit 及其 commit message，不能据此推出测试通过、已推送、已部署或目标环境已验证。证据和交付边界放在其真正适用的最小范围：整条主线共享时统一说明；只有某个变化方向的证据等级或完成层级不同，就紧跟该方向说明，不把局部证据扩大成整条主线的共同终态。

### 先定义这项工作

组织每条核心主线时，先用一到两句写出工作定义：这项工作在处理什么对象，做什么动作，想解决或确认什么，以及范围到哪里。工作定义必须说清动机与收益，而不只是动作：原来的状态哪里不成立、这次改成了什么、因此本人以后少付出什么代价或多了什么能力。只写“把 A 调整为 B”而读者看不出为什么值得调整的，属于未完成的工作定义。工作定义是“事情本身”的入口，不要求绑定单一项目、仓库或 `project_key`；跨项目事项按实际对象合并，归属不清时以任务正文和目标对象为准。

标题和首段应让读者只看这两处就能复述工作范围。不要只写“文档同步”或“资源整理”这类工具标签，应具体到处理了哪类资料、进行了什么动作、形成了什么可判断结果。结论必须以完成态出场，再展开细节：先写“某某完成了什么、现在是什么状态”，然后才是背景、关键动作和边界；不要用动作式的半截句子承担结论位置，也不要在读者还不知道这件事是什么之前，先抛出过程中的判断。

核心主线在不能说明以下内容时不得进入定稿：

- 为什么做，原来的状态哪里不成立；
- 做了哪些关键动作，判断如何变化；
- 最终结果是什么，由什么证据证明；
- 这件事换来了什么：新增或恢复的能力、被消除的风险、被省掉的重复代价，或被推进的关键判断；
- 哪一层已经完成，哪一层仍未完成。

以上是主线级语义完整性检查，不要求每个变化方向分别具备一套固定字段。标题或上下文已经表达的信息无需重复。

完成标准：每条核心主线都有闭合的因果链和分层终态；中间观察没有覆盖后续已验证结论；引用到的不完整证据都有边界。

## 五、写自适应初稿

### 叙述视角

日报是本人自己的工作记录，不是 Agent 的执行汇报。正文以本人为叙述主体：这一天要解决什么、判断怎么变化、做到哪里。

- 叙述主体默认省略人称。不用“我”“本人”作主语，句子直接从动作和结果起笔（“产出国内会议室一页纸汇报并完成知识库整理”）；只有需要把本人的动作和他人的动作区分开时才点名对方。
- 句子主干写本人做成的事，不写他人的诉求、材料的状态或事情的整体经过。先写产出了什么、把什么改成了什么，再把对方的要求、初稿的问题作为原因或背景放进后半句。
- 不写“经本人确认”“在明确授权后”“用户要求”这类描述 Agent 自身权限来源的表述；授权关系属于运行边界，只在真的改变了结论范围时才出现。
- 不把 Agent 的执行姿态当成工作内容。“读取了哪些文件”“调用了哪个命令”“扫描了多少条记录”只是取证过程，不进正文。
- 判断和取舍写成本人的判断。被推翻、纠正或重新定位的地方要写出来，这类转折往往比最终结果更有价值。

### 不写防御性说明

分层终态只用肯定式写清做到了哪一层，不补否认更高层的免责句。“这些是汇报与知识管理动作，不代表系统功能已生产上线”“该结论不构成……”“仅代表本地验证”这类为免责而生成的句子一律不进正文，它们不增加读者可用的信息。读者确实需要的边界写成具体状态：“知识库整库已发布”“改动已提交到本地，未推送”。仍未闭环、且会改变下一步的缺口进入“后续关注”或“证据与边界”，同样用肯定句写当前状态。

### 结构

以下是常见结构的参考，不是必须逐节填满的合同。章节名称、顺序和数量都由当天真实内容决定：

```markdown
# 当日概览

用最短可扫描形式交代当天重心和总体状态，不重复后文。扫描计数等机械审计信息由 frontmatter 承担，只有会影响正文结论的证据缺口才披露。

## <核心主线的自然语言标题>

先给出当前结论，再按变化结构说明主要变化和做到哪里；多条时按真实重要性排序。

## 其他进展

合并次要但值得保留的事项。

## 后续关注

只写已有证据支持、确实需要继续推进或等待的内容。

## 经验与问题

仅在形成可复用认识或真实踩坑时出现。

## 证据与边界

逐条简短，只交代结论的可信范围：会话覆盖与缺口、账本变更的性质、代码提交的范围、聊天证据的相关性；末尾一句写清当天有哪些动作真的到达了本机之外。不复述正文事实，不展开机制细节。
```

每条主线按第三节判定的变化结构选择表达形态，不使用固定栏目、固定要点数量或统一标签。共享信息在主线层只写一次，局部差异贴近对应方向。读者应先看到当前结论，再选择是否阅读变化过程；段落和列表各自只承载一个清晰语义，如果必须读完整个长段才能找到当前结论、各变化方向或完成边界，就按变化结构重新组织。

### 事实与措辞

每条事实必须来自 Activity、Work event、Git commit evidence、DChat evidence 或本人补录；正文不写 ID。内部标识同样不进正文：Case 编号、commit 短 SHA、节点名、文件行号、批次名这类只在当时上下文里成立的记号，要么翻译成读者能理解的现象，要么省略；确需区分具体对象时用它的实际含义指代。Git 的 `commit_message` 和 DChat 原文都是辅助线索，不能代替对实际工作结果的判断；没有 Git commit 或没有 DChat 消息也不能反推没有工作。

价值是可使用或可验证的新能力、被消除的明确风险、得以推进的关键判断，或可复用且能降低未来成本的认识；修改动作本身不是价值。踩坑是合理路径因隐藏约束失败、证据误导判断，或系统产生非预期行为，并经过定位形成了可复用的避免方式；普通修错、参数变化和未完成事项本身不是踩坑。不为固定篇幅制造价值、踩坑、经验或后续安排。

简洁的下限是语义完整，不是字数少。核心主线宁可多写两句把动机、关键判断和收益说清楚，也不要压缩成一句只有动作的摘要；真正该删的是取证过程、机制细节、重复的边界声明和为了凑齐版式而生成的内容。修订既有日报时按同一标准复核全篇，不只修补被点名的那几处。

完成标准：正文以本人为叙述主体，没有人称主语、Agent 执行姿态、授权表述和防御性免责句；当天投入最大或反复纠偏的工作没有被降级；只看每条核心主线的标题和首段即可复述其对象、当前结论与范围；读者不打开证据也能理解这项工作是什么、为什么值得做、换来了什么和做到哪；不能复述时回查相关 Activity 的 `pack` / `show`，以实际对象补齐表述。

## 六、只问实质问题

默认不提问。仅在以下情况提问：

- 两个可靠来源对最终事实直接冲突；
- 真实系统不可读取，且缺口会改变核心结论；
- 需要本人选择责任、范围、授权或外部状态；
- DChat 群聊与项目清单出现稳定新增或冲突关系。确认前只保留为本次日报判断和 `unresolved`，不修改项目清单；私聊归属始终只用于本次日报，不持久化。

已有终态证据、内容取舍、是否保留次要事项、是否叫“踩坑”以及如何组织措辞都由 Daily 自行判断。问题必须带具体证据，并说明答案会改变哪项事实或动作；未解决的实质缺口才计入 `unresolved`。

Daily 发现“后续要做”只决定日报如何表达。只有本人另外明确要求写入 LifeOS Work，才把原话和来源交给顶层 Work create-only 分支；Daily 不拼写 Work CLI，也不生成幂等键。

完成标准：每个问题都命中事实、权限或外部状态门；没有编辑性问题；未授权候选未进入 Work。

## 七、写入与确认

使用 `lifeos reports write` 写入既有 draft，不直接编辑 `begin` 返回路径；正文文件只含 Markdown，frontmatter 由 CLI 拥有，字段与选项以 `--help` 为准。

计数与 ID 的口径：`activity_ids` 是第二节那份完整 index 的去重 Activity ID，格式为 `ACT-` 加 24 位 Base32；`sessions_partial` / `sessions_interrupted` / `sessions_omitted` 同样只来自这一份 index，按 `session-evidence.md` 的定义取值；`work_event_ids`、`git_commit_ids` 和 `git_commits` 只记正文实际引用的对象。`git_commit_ids` 使用稳定的 `repo_key@完整 SHA`，不使用 LifeOS 另造的 per-commit ref；`project_key` 在 Git scan 时由当前 Project Catalog 即时解析，不复制进日报 ID。

本人明确确认后才运行 `lifeos reports confirm --day <YYYY-MM-DD>`，随后运行 `lifeos reports validate`。

完成标准：正文、计数和 ID 清单通过 validate；没有本人确认时状态保持 draft。

## 边界

Daily 分支不生成周期报或复盘，不写 Obsidian；周、月、季度、半年和年度总结转顶层 Periodic 分支。不关闭、改期或变更已有 Work 事实，也不替本人确认。Git 证据只读本地显式注册仓库，不上传、不访问 remote、不保存完整 diff、changed paths、author email 或未提交状态。DChat 只读结构化类型为 `p2p / extp2p` 的私聊和当前项目清单声明的群聊，不发送消息、不修改 DChat、不下载附件本体；DChat 声称的完成或上线必须由更高等级证据核对。
