# Daily 工作流

## 原则

日报是写给一个月后的本人看的。那时他已经忘了当天的细节，打开这一页先要知道这一天做成了什么：做出了什么东西、哪件事变成了什么样、现在能拿它干什么。再往下，他要找回的是自己的判断：促成这些结果的决定和理由，做错的决定和事后的反思，也包括做对的决定和它为什么对。一个没遇到困难就达成的结果，如果背后有一个正确的选择，那个选择和理由同样写进所属主线，因为下次还会用到。偶尔还有一样：当天真正想明白的事。它不是每天都有，没有就不写。这些决定正文写什么，其余一切都是取证过程。

判断只有两种来源可以进正文：本人自己说出的，也就是会话、聊天或补录里的推翻、后悔、「当时以为」「早该」这类原话；以及能对照核验的，也就是后来的事实推翻了先前的决定、动作违背了既有约定、结果离项目里程碑还有多远。写作者自己对这一天的观感，比如效率高、决定正确、进展顺利，没有这两种依据就是自说自话，一句不写。

取证过程留给写作者自己：会话、账本、提交、聊天和本人的补录是用来判断「今天到底做到哪」的材料，判断完成后材料退场，正文只写判断的结果。每一句都先问：一个月后的本人读到这句，得到了什么？得到的应该是做成了什么、为什么这样定、接下来卡在哪；得不到这些的句子，不论多真实、多费力，都删。只证明某件事做过、查过、测过、核对过、看过的句子，比如「两边数字一分不差」「主链路已实测」「都看过没有问题」，给读者的只是安心：证据决定一句话能写到哪一层，证据本身不进正文。按这个测试，活动清单、审计信息、流水线阶段名、免责句和只在当时上下文里成立的记号都出不了门。

篇幅是这个测试的副产品，不是目标：写清做成了什么和促成它的判断所需的句子都留，多一句都不留。宁可一天只有一条主线加三行「还做了」，也不为版式补内容。

## 定位

一天一份事实性日报，写进 Private Runtime，由本人确认。它不要求每天都有价值、踩坑或经验。Git 提交和 DChat 是可选的辅助证据，不替代 Agent 会话、Work 或本人补录，也不能单独定义当天是否工作。读取来源证据不产生 Work 写入授权，确认日报也不等于确认 Work。

本文件拥有流程顺序、主线判断和正文表达。证据语义、采集门细则、计数口径和结论强度由 [`session-evidence.md`](session-evidence.md) 拥有，DChat 采集、消息证明力与项目确认由 [`dchat-evidence.md`](dchat-evidence.md) 拥有；这里只写触发条件和它们如何改变当前动作。

## 一、取得窗口

```bash
lifeos reports path --day <YYYY-MM-DD> --json
lifeos reports begin --day <YYYY-MM-DD> --json
```

目标日默认今天。先用只读的 `path` 取得状态和唯一自然日窗口；日报尚未确认、需要建立或覆盖 draft 时再执行 `begin`，并核对两者返回的 `window.from` / `window.to` 完全一致。已确认日报保持不变；本人只要求重新采集证据时，直接使用 `path` 返回的窗口，不调用 `begin`，也不自行做日期运算。只有本人明确要求重做日报时才使用 `begin --redo`。

完成标准：目标状态和唯一自然日窗口已取得；重做时旧快照已由 CLI 留存。旧快照只在本人明确要求清理时用 `lifeos reports prune --apply`（可加 `--day`）删除，不随重做或确认自动清理。

### 承接上一期

用 `lifeos reports list --to <目标日> --json` 查看此前日报的日期和状态，从近到远读取已确认正文，找到最近一份有实际工作内容的日报，提取「待办与依赖」和「需要关注」后停止回溯；旧版「欠与等」作为待重新筛选的线索。纯休假且没有工作内容的日报跳过；休假期间有实际工作或跟进结果的正常承接。休假依据本人确认或已确认日报，日期、空会话和无提交不能代替这一判断。

中间缺报或只有草稿时，保留记录缺口；草稿只作核查线索。先以最近一期符合条件的已确认日报为承接起点，缺口可能改变某项终态时只补查该项在间隔内的证据。没有前期日报时，从当天事实开始。旧日报没有这两节及旧版「欠与等」时按空清单处理，不继续翻找更早已退出的事项；这一机制从当前可见清单接续，不替代历史漏项审计。

承接和核对均以目标日结束时为界；当前账本、项目文档和需求状态须结合结果实际发生时间还原，之后才发生的结果留在之后的日报；时间无法确定时保留日期缺口。间隔内补查只用于更新旧事项，发生在其他日期的工作不计作目标日成果，其证据也不混入当天 Sessions 计数。

完成标准：已确定承接日报或无前期日报；休假、缺报和草稿已区分；上一期各项已进入第三节核对清单，可能影响结论的间隔已明确。

## 二、盘点并审计证据

读取正文、判断 Activity、处理生命周期或填写 frontmatter 前，先读 `session-evidence.md`，本节的采集门、完整性判据、异常审计清单和计数口径全部按该文件执行。运行 `lifeos dchat validate --json` 判断独立 DChat Evidence 是否已配置；配置有效时再读 `dchat-evidence.md`。运行 `lifeos calendar validate --json` 判断日历来源是否已启用；启用时再读 [`calendar-evidence.md`](calendar-evidence.md)。尚未配置只表示这一路尚未启用，不阻塞其他来源形成日报。

```bash
lifeos sessions scans --from <window.from> --to <window.to> --json
lifeos project discover --json
lifeos project validate --all --json
lifeos sessions validate --scan <scan-id>
lifeos sessions scan --source all --from <window.from> --to <window.to> --json
lifeos sessions index --from <window.from> --to <window.to> --json
lifeos work changes --from <window.from> --to <window.to> --json
lifeos git scans --from <window.from> --to <window.to> --json
lifeos git scan --from <window.from> --to <window.to> --json
lifeos git validate --scan <git-scan-id> --json
lifeos dchat validate --json
lifeos dchat scans --from <window.from> --to <window.to> --json
lifeos dchat scan --from <window.from> --to <window.to> --json
lifeos dchat index --from <window.from> --to <window.to> --json
lifeos calendar validate --json
lifeos calendar scans --from <window.from> --to <window.to> --json
lifeos calendar scan --from <window.from> --to <window.to> --json
lifeos calendar index --from <window.from> --to <window.to> --json
```

按以下顺序执行：

1. 先运行完整 `project discover` 与 `project validate --all`，记录当前发现根、有效项目和 findings。新合法清单无需 Work 跟踪即可参与项目映射；单个非法或冲突项目只影响该项目，但如果可能改变日报主线归属则保留 Pending。
2. 过 Sessions 采集门：查目标窗口的 `sessions scans`，按 `session-evidence.md` 判断能否复用并校验选中的 `scan_id`，否则执行一次精确窗口的 `sessions scan --source all` 再校验。随后读取无过滤的完整 index，并完成其中的异常审计。来源不可读、校验失败，或覆盖与异常不足以支撑结论时，停止定稿并报告具体 Pending；不要把空 index 写成“昨日没有工作”。
3. 读取窗口内全部 Work changes。它们证明 LifeOS 账本发生了什么变化，不自动证明对应项目已经交付。
4. 有显式注册的 Git 仓库时必须执行 Git 检查门：先读目标窗口的 `git scans`，可复用快照须通过 `git validate --scan`，否则按需运行一次 `git scan`。Git scan 只读本地提交历史、写入私有证据快照，不修改仓库、不访问 remote、不写 Work。Git 不可用、没有注册仓库或扫描失败，不自动等于当天没有工作；只有当日报结论依赖 Git 且缺口影响事实时，才披露 Pending 或提问。正文出现任何提交、推送、部署层级断言时，对应仓库窗口内必须有通过校验的快照，否则该断言降级为“会话陈述”。
5. 本人主动提供的补录作为第三路证据；没有实质缺口时不为了凑齐输入而提问。
6. DChat 已配置时，按 `dchat-evidence.md` 通过精确窗口 scan 和 validate 后读取完整 index，只对可能改变工作主线或承接事项状态的会话渐进调用 pack。可读 scope 只采用 DChat 的结构化会话类型与当前项目清单中的群 VID，不按账号名称、头像或消息内容猜测身份，也不用群名、活跃度、本人是否发言或关键词扩大范围。
7. 日历已启用时，按 `calendar-evidence.md` 通过精确窗口 scan 后读取 index，按性质、证据、名单三步形成「准备记入」和「剔除」两张清单；日历只证明排了会，去没去由本人确认。

完成标准：Sessions 采集门与完整 index 已通过 `session-evidence.md` 的判据；所有可能改变自然日事实的异常已有解释或 Pending；Work changes 已读取；Git 检查门已执行且失败与缺失边界已解释；DChat 已配置时其采集门与项目清单冲突已处理，未配置时没有把缺失解释成“没有聊天工作”；日历已启用时两张会议清单已形成。

## 三、筛选本人待办、依赖与关注

先按本人职责和实际需要筛选，再核查入选结果的状态。深读或本人补录带来新候选、完成线索或责任变化时，回到对应记录重判，再更新正文。本节准入同时约束正文中的承接项、要求本人跟进的问题，以及新增或延续本人跟进的关联候选；已核实变化对应的完成、退出和事实修正仍按第七节检查。

### 职责与准入

从本人说明、已认领任务及项目分工确定本人负责的结果和关注层级；存在私人 `~/.config/lifeos/agent-profile.md` 时，读取其中的日报关注视角。具体事项以本人最新明确说明为准。项目负责人身份、群聊参与、别人已认领或项目尚未完成，都不能单独证明本人要承担执行或协调动作。职责不明时先查已有直接来源；仍不明且没有本人关系的直接依据时，留在核对材料；已有具体关系、但持续责任或关注价值存在合理分歧时，按第七节列待本人判断的候选。

两类内容分别判断，同一事项采用最具体的一类：

- **待办与依赖**：本人已接下、仍有效的交付或协调承诺；或本人当前推进已承担的工作确实需要取得的外部结果。写清本人要交什么，或等谁提供什么、它支撑本人的哪一步。对方承诺反馈只证明对方有动作，只有本人需要这个结果时才构成本人的依赖；对方继续处理、必要时再来找本人的事项，在新诉求发生后重新判断。
- **需要关注**：本人明确要求持续关注，或已有事实显示某项变化、风险、临近节点会影响本人职责范围内的交付判断或关键决定，但当前尚无本人待执行动作或具体依赖。写清发生了什么、为什么与本人有关，以及已有的触发条件或约定节点。只有项目相关性、普通进度或客观未知的，留在来源中。仅为“可能以后需要”不创设关注项、检查日期或催办动作。

先按项目职责选择结果层级，再按具体事项判断是否进入上述两类。本人全程负责的项目可以涉及实现、接入和交付细节；他人负责执行的项目围绕本人负责的产品、协调或项目结果表达。两种情形都按实际承诺、依赖或关注依据筛选，不展开全部未完成步骤。

本人明确退出某项责任或关注时，退出对应部分，其他已成立的承诺、必要依赖或关注分别判断；三者均无依据时退出两类内容，业务是否完成独立判断。已有本人承诺或明确关注仍有效时，沉默和经过多日不构成取消依据。历史日报只提供线索，每项继续承接都须指向本人责任、依赖或关注的直接依据；误收项退出不要求本人逐条声明放弃。

### 建立核对记录

给上一期每项和当天新增候选各留一条可回查的记录；记录留在本次对话或临时工作材料中，供写作和验收使用。按交付对象、接收方、阶段和完成条件区分事项；同一人参与、名称相近或同属一个项目只作定位线索。可分别完成的结果拆开核对并保留与原项的对应。

| 核对内容 | 必须说清的事实 |
| --- | --- |
| 原项与结果 | 原来源、交付对象、接收方、阶段与完成条件；拆分后的各个结果 |
| 本人关系与准入 | 本人负责什么；具体承诺、依赖的下一步或关注影响及直接依据；进入哪一类或为何不纳入 |
| 核查范围 | 上次有直接依据的状态及实际日期；已查来源、日期和未覆盖区间；重复抄录日期不充当依据日期 |
| 最新结果 | 截至目标日结束能成立的状态、来源和实际发生时间；补录收到时间另记 |
| 当期去向 | 保留、更新、完成退出、取消或替代退出、本人不再承担或关注、Work 已承接、远期候选或待本人判断；取证缺口单独记录 |

### 核查状态与去向

完成、取消、交接或不再关注的直接依据已足以确定去向时，核对到该层即可。需要继续承接的旧项，若依据早于上一期、连续沿用却无直接核查依据，或出现早已完成的线索，从上次可靠依据查到目标日结束；起点不明时回查原来源，仍不明则记录范围缺口。只补查该事项尚未覆盖的区间，复用已核实材料。跨休假或缺报按同一范围处理，抄录不缩短核查区间。

对照所属项目当前入口，沿已有引用查一跳到对应记录；没有项目入口时回查原来源。存在完成、上线、答复或冲突线索时，读到支持该结果的证据。聊天反馈按 `dchat-evidence.md` 核对，会话终态按 `session-evidence.md` 渐进深读。补查按实际发生日归属，目标日外的成果与证据不计入当天成果和 Sessions 计数。

已有完成依据时，后续异常须证明同一结果失效、遗漏或需要返工才重开原项；独立问题按自己的责任和影响核对。答复只解决一部分时，已解决部分退出，剩余结果重新过准入。

尚未查到结果属于写作者的取证缺口，不产生本人待办、依赖或关注。先完成可执行核查；不可读或冲突会改变核心结论时按第七节处理。已有本人承诺或必要依赖且仍有效的，保留已成立的约定和日期；核对材料记录最新结果未知，正文不把未知写成“仍未完成”“需要催办”或逾期，也不自动顺延。状态不确定性确实影响本人决定时，只在交付说明中指出需补读的来源和影响。

用 `lifeos work entries --kind task --live` 按项目、目标、本人责任和完成条件匹配结果，匹配上的用 `lifeos work show <ID>` 回读。已有 Work 承接的待办不在日报重复展开；当天重要变化可进主线或「还做了」，具体差异按第七节提出更新候选。

每个结果自上而下取第一条适用去向：

| 核对结果 | 当期去向 |
| --- | --- |
| 已完成、收到答复或阻塞解除，满足原完成条件 | 完成退出；目标日成果按主线或「还做了」准入收录 |
| 已明确取消或被替代 | 原项退出；替代后的结果重新过准入 |
| 有具体事实及本人关系依据，但是否纳入仍有合理分歧 | 按第七节列入交付回复的「待你判断」，选定前不进正文、不自动跨日承接 |
| 本人无剩余承诺、必要依赖或关注依据 | 退出两类内容；业务完成状态保持独立；历史误收不转成确认问题或新增 Work 候选 |
| 已有 Work 正文与负责人表达了该待办或依赖 | 不在日报重复展开；变化按第七节核对更新候选 |
| 待办或依赖已约定下一节点，且晚于目标日后十四天 | 不逐日承接；交付时列为待办候选，本人确认后交 Work 分支，其余退出；远期本身不构成关注依据 |
| 符合待办与依赖准入 | 按已成立的承诺或必要依赖简短保留，写已有约定日期；只用新证据更新状态 |
| 符合需要关注准入 | 按本人关注的结果层级保留；关注引发具体动作或依赖时转入前一类，不两处重复 |

按项目归组，同一结果的催办、联系、确认合成最新状态，可分别完成的结果分行。主线已说清的同一变化不重复背景。无合格项时省略相应章节。纯休假且无实际工作时可省略两节，下一工作日报仍按「承接上一期」接续。

完成标准：所有旧项、新候选及拆分结果都有准入依据和去向；保留项逐一对应正文，退出项未以关注、提问或候选形式重新出现；取证缺口与本人责任分开，已入 Work 的事项不重复展开。已有可读的完成或冲突线索影响正文时完成核查再写入；关键事实仍无法成立时按第七节处理。

## 四、建立工作主线

承接事项核对完成后，再选主线与需要深读的 Activity。Activity 是 evidence activity，不是任务、项目或日报章节；允许把多个来源、并行子 Agent 或多个 `project_key` 的 Activity 合并成同一工作主线，也允许把目标发生变化的长 Activity 拆成不同阶段。

工作主线以共同目标和可共享的总体终态为边界，不以项目名、仓库、对话或修改文件数机械分组。同一项目内目标和闭环状态彼此独立的工作可以拆成不同主线；不同项目只有在任务正文或交付证据明确表明它们共同服务于同一交付对象，且能够共享一个不冒充任一项目的总体终态时才合并。部门、主题、工具、群聊或名称相近不构成共同目标。

### 三层准入

日报的单位是状态增量，不是活动覆盖。每个 Activity 按它对当天的贡献落进三层之一：

- **核心主线**（最多三条）：本人当天明确要推进、投入最大、或经历过推翻与重新定位的工作。判据是它改变了可用能力、交付状态、项目判断、责任边界或实质风险中的至少一项，或者当天发生了关键纠偏。仍在进行中不影响入选：投入最大的工作即使没做完，也是当天的重心。
- **还做了**（最多十条，每条一行）：改变了某个对象的状态、日后可能要回头查的事，一句话写清对象和终态即可。例：某份材料发给了谁、某项外部反馈收到、某个口径与谁对齐了。
- **不进正文**：不改变任何对象状态或判断的动作，以及只对 Agent 自己有意义的流水线事件。前者如本机维护、依赖升级、查资料、格式清理、例行巡检、重复执行的检查、同步安装副本、日报草稿的生成与确认；后者如本地提交、分支、Tag、测试或 Gate 通过、规格文档建立、候选版本号、发布到某环境的动作本身、待办的关闭与改期。它们发生过这件事由 frontmatter 的计数和 ID 承担，正文一字不写。

同一件事在核心主线和「还做了」里只出现一次。三条以上的工作都够核心主线标准时，按投入和纠偏强度排序取前三，其余降到「还做了」；「还做了」超过十条时先合并同一对象的条目，仍超出的按日后被回查的可能性取前十，其余不进正文。没有达到核心主线准入的工作时，概览一句加实际成立的章节即可；休假期间的工作和沟通同样按实际结果判断。

### 项目边界审计

`project_key` 不能单独决定业务主题，它与 `workspace`、`changed_targets` 共同构成边界证据；DChat 会话候选只限定搜索范围，不覆盖已核验 Activity 的归属。

写初稿前，为每条核心主线回看这三项与任务对象：标题含具体项目名时，纳入内容必须属于该项目或确有证据属于该项目交付；不同项目只是主题相近、没有共同交付对象时立即拆分。确需跨项目合并时使用中性标题，分别说明各项目贡献与边界。

### 变化结构

为每条核心主线判断变化结构。它决定深读到哪、正文展开到哪，不作为正文标签：

- **简单变化**：围绕一个对象形成单一结果。读到结果和边界即可，一段写完。
- **多方向变化**：同一目标下有多个能分别说明的变化。按真实对象归并，写总体结论加两三个短要点；每个方向只写结果，不各自重复问题、纠偏和边界。
- **多轮变化**：同一方向经过验证、反馈或纠偏，后续判断替代了早期判断。只深读实质改变最终方案、完成状态、风险或下一步的关键转折；写最新结论和那一次转折的原因，被后续结果覆盖的中间状态省略。
- **混合变化**：多个方向中只有部分发生多轮变化。按方向拆分，只展开发生关键纠偏或存在独立风险的方向。

只有变化会改变可用能力、项目判断、责任边界、交付状态、实质风险或下一步时，才把它作为独立方向。多个文件修改、参数调整、重复测试、措辞迭代和界面组件级调整，都并进所属方向的一句结果里。

完成标准：每个 Activity 都落进三层之一；核心主线不超过三条且反映当天真实重心；并行分支已归并，混合目标已拆开；每条核心主线的变化结构已确定；项目边界审计没有发现被单一项目标题吞并的异项目工作。

## 五、渐进深读与终态收敛

按 `session-evidence.md` 的渐进深读执行：核心主线读全部相关 Activity 的 `pack --activity`，承载关键终态、验证或冲突的 Slice 再用 `show` 回查；「还做了」读到对象和终态成立即停；不进正文的活动留在 index 粒度。partial 和 `interrupted_with_result` 只在承载被引用事实或可能改变终态时深读。

深读核心主线时单独摘出本人的判断原话：拍板时给的理由、推翻前一天决定的那句话、对自己动作的评价（「当时以为」「早该」「不该花这么久」）、听到对方反馈后的改口。这些句子是主线里决定和理由的直接材料，也是「想明白的」里「本人亲口说出的道理」的唯一来源；摘出后再对照该主线在项目 CURRENT、DECISIONS 或本人会话里的目标，判断这一步离目标还有多远。

每条核心主线先收敛最新结论，再按已确定的变化结构整理支撑它的内容。需要保留多轮演变时，按 `最新结论 → 关键转折及原因 → 证明力最强的最新证据 → 剩余边界` 组织；没有纠偏时不补造转折。终态优先级取决于证据能证明什么，而不是哪句话最肯定。

交付层级按 `session-evidence.md` 的链条核对，前一层不能推出后一层；Git 提交只能证明对应仓库在该窗口产生了 commit 及其 commit message，测试通过、已推送、已部署、目标环境已验证各自需要自己的证据。这条链是写作者判断「今天到底做到哪」的依据，不是正文内容：正文只写它对世界的结果，并且只在结果会改变本人下一步或当前风险时写。写法是说清谁现在能用、什么还是旧的、什么还没在真实数据上跑过：「线上还是旧链路，新求解还没碰过真实报价」「Demo 已发研发群，本地又改了一轮还没重发」。提交、Gate、分支、Tag、候选号、发布动作这些阶段名不出现在正文里。

### 每条核心主线写什么

每条主线先说清这一天做成了什么：用大白话写做出了什么、哪件事变成了什么样、现在能拿它干什么。主线首次出现或目标改变的那天，再用一两句交代原来哪里不成立；交代背景是为了推出这一步，接不上的背景不写。此后延续的日子只写增量，背景由上一期已确认工作日报承担。

接着写促成它的那一两个决定：选了什么、放弃了什么，理由一句，本人的原话优先于转述。做对的决定被后续事实证明了，写它被什么证明，顺利的日子也照写；做错的决定进主线的门槛是本人自己认了，或后续事实推翻了它，写清原先依据什么、现在为什么不成立，并归因到人：我判断错、前提变了，还是对方给的信息错。转折只认本人的判断或前提的变化，多轮变化的主线以它为骨架；纠正 Agent 的误读、改它的草稿、追问它为什么停早，是过程，正文只留纠正后的决定。Agent 反复出现同一类毛病、本人因此换了做法时，写这个毛病和应对。同类决定很多时，比如一批产品规则或一组口径，挑最有分量的一两条带理由，其余由项目文档承接。

还卡着、会改变下一步的缺口，写成现实里的状态和责任方。能说出这一步推进了项目 CURRENT、DECISIONS 或本人说过的哪个目标、离终点还差什么时，写一句；说不出就不写，不用「往后可以……」这类泛泛的收益句补位。写什么看这条线当天真有什么，不按固定的问题逐项补。

原型、页面、文档打磨类工作按「交接给研发、评审或调研对象时会不会提」定粒度：会提的写（原型进入可评审、发给了谁、评审结论是什么、哪条规则被撤回），不会提的并进一句结果（组件尺寸、间距、字重、抽屉高度、措辞迭代）。

完成标准：每条核心主线说清了当天做成了什么，每个拍板带理由，每次推翻带归因，写进去的转折都是本人的判断或前提的变化；首次出现的主线交代了原来哪里不成立，延续的主线只有增量；中间观察没有覆盖后续已验证结论；引用到的不完整证据都有边界。

## 六、写初稿

### 骨架

骨架固定，每天一致，让读者建立阅读习惯；内容不成立的章节整节省略，不为版式凑数。

```markdown
# 当日概览

三句以内：先点今天最要紧的一件和它为什么要紧，再说总体到了哪一步。只写后文没有的判断，不预告章节。

## <核心主线一句话标题，写做成了什么>

**一句加粗结论：先说清这一天做成了什么，再带上这条线最有分量的那个决定或变化。** 随后一段两百字以内，写促成它的决定和理由，以及确实还卡着的地方。多方向变化可用两三个短要点，每个要点只写结果。

## 还做了

- 一行一条，最多十条，写对象和终态。

## 会议

- 起止时间 名称 — 服务的项目或需求（部门例会、培训这类写性质）；只写本人确认参加的会，末行写「共 N 小时。」。日历未启用或当天没有会时整节省略。

## 待办与依赖

<项目名>
- <本人要完成的结果与已约定日期>；或<本人哪一步需要谁提供什么与已约定日期>。

只写第三节准入且未被 Work 承接的事项。归不到项目的放「其他」，同一结果一行；只有本人交付或外部依赖一侧时只写该侧。没有已约定日期就省略日期。

## 需要关注

- <变化、风险或节点>：<为什么影响本人负责的结果或判断>；<已有的触发条件或约定节点，如有>。

按第三节准入和本人职责定粒度。没有具体动作时不补造待办；主线已说清背景时，本节只保留关注对象及已有触发条件或节点，以便下一期接续。无合格内容时省略整节。

## 想明白的

只收两种：当天出现的落差，也就是本人原来的判断或做法被推翻、原因已经弄清；本人当天亲口说出的道理。每条一段，段首先给认识本身，再给它来自当天哪件事。大多数日子没有，整节省略。
```

篇幅上限：常规日 2,000 字，发生重大转折的日子放宽到 3,500 字；这是上限不是目标，内容少的日子就写得短。超出时先删「还做了」的从句和核心主线里的过程细节，再考虑合并方向。核心主线最多三条，每条正文两百字以内，只有多轮变化需要交代转折时可到三百字。

「待办与依赖」和「需要关注」按第三节核对结果成文，无变化的承接项不计作当天成果。压缩全文后仍超篇幅时，保留全部合格承接项，允许这两节所需篇幅超出总上限。

「想明白的」只收两种。一是落差：本人原来以为的或做的，被事实、别人或自己推翻，而且原因当天已经弄清；踩坑属于这一种，要已定位出下次怎么避开。二是本人当天亲口说出的道理，以原话为准。写作者从当天某个决定里归纳出的道理不算，不论它听上去多有道理。以下三种即使沾上了这两类也删：主线里已经写过的决定换一种说法；不看当天也成立的通用道理，比如「展示结构要从使用出发」「文档写了不够」；为了显得能用而补上的「以后……先……」。普通修错、参数变化和未完成事项同样不算。这一节不设条数和字数份额，大多数日子整节省略。

审计信息只由 frontmatter 承担：会话来源覆盖、partial 计数、账本变更条数、Git 快照范围、聊天消息数、到达本机之外的动作清单，这些都不进正文，也不改写成散文句放进概览或主线。只有证据缺口实质改变了某条结论的可信范围时，在那条主线内用一句肯定句写清当前能成立到哪一层。

### 叙述视角

日报是本人自己的工作日志。用第一人称写判断、取舍和纠偏：「我推翻了」「我决定」「我原以为」；动作和结果可以省略主语直接起笔。需要把本人的动作和他人的动作区分开时点名对方。他人的诉求、材料的状态、事情的整体经过放在后半句作原因或背景，句子主干始终是本人做成或决定的事。段落开头的动词交替使用，同一天里避免连续几段都以同一个词起笔。

Agent 的执行姿态不是工作内容：读取了哪些文件、调用了哪个命令、扫描了多少记录，只是取证过程。授权来源同理，只在真的改变了结论范围时才出现。对本人的评价只引本人原话或对照事实，写作者的观感不进正文。

### 边界的写法

边界只写会改变下一步或风险的那一条，用它在世界里的样子说：「派单修订已上线，明天首轮运行才知道分组对不对」「Demo 已发研发群，本地又改了一轮还没重发」。已经闭环的事不写边界，读者据此自己知道还差什么，免责句和阶段名不提供额外信息。仍未闭环且影响下一步的缺口在所属主线交代影响；需要持续承接且符合第三节准入的，分别在「待办与依赖」或「需要关注」简短保留，不重复背景。

### 事实与措辞

当日新增事实来自 Activity、Work event、Git commit evidence、DChat evidence 或本人补录；上一期已确认日报只支持承接其中的历史承诺和状态，更新终态需要相应新证据。正文不写 ID。内部标识同样不进正文：Case 编号、commit 短 SHA、节点名、文件行号、批次名这类只在当时上下文里成立的记号，要么翻译成读者能理解的现象，要么省略；确需区分具体对象时用它的实际含义指代。钟点只在它是约定的时间点时出现（会议、演示、定时任务的时刻）；某个动作发生在几点几分不写，「凌晨」「晚间」这类粗粒度已经够用。Git 的 `commit_message` 和 DChat 原文都是辅助线索，不能代替对实际工作结果的判断；没有 Git commit 或没有 DChat 消息也不能反推没有工作。

数字只在改变判断时出现：通过率从 62% 到 82%、问答记录从 320 行压到 139 行，这种写；提交条数、测试条数、消息条数、截图张数、文件份数一律省略。

简洁的下限是语义完整。核心主线宁可多写一句把转折原因说清楚，也不压缩成只有动作的摘要；该删的是过程细节、重复的边界声明和为了凑版式生成的内容。修订既有日报时按同一标准复核全篇，不只修补被点名的那几处。

完成标准：骨架与上文一致；核心主线不超过三条、每条的加粗结论说清了当天做成了什么；「还做了」不超过十条且每条一行；「想明白的」每条都指得出是哪个落差或哪句原话；正文里没有审计信息、ID、免责句、流水线阶段名、无判断意义的数字，也没有只证明做过、查过、核对过的句子；篇幅遵循上述上限及两类合格承接项完整保留的例外；只看概览和各主线的加粗结论就能复述这一天，并说得出当天有没有做错的决定。

## 七、补充与关联更新候选

### 待本人判断的内容候选

完成可执行核查后，事实已成立、与本人关系有直接依据，但是否值得持续跟进或关注仍有两种合理处理时，在交付回复中列「待你判断」。明确符合或不符合准入的自行处理；仅缺终态、普通项目相关、无本人关系依据或本人已明确排除的，不列候选。

每项简短写出已知事实与来源、与本人的关系、拿不准的具体原因和建议去向，供本人选「纳入待办与依赖」「纳入需要关注」或「不纳入」。只问有分歧的取舍，不要求本人重查材料。无此类候选时省略该区。

候选在选定前留在交付回复，不进入日报正文或 Work，不自动跨日承接，也不阻塞其余可信内容成稿；它属于内容选择，不计作事实缺失的 `unresolved`。未回应的候选保留原回复入口，仅在本人询问或事实、责任有实质变化时重新提出。本人选定后按实际发生时间更新未确认草稿；仅说确认日报不视为选定候选，选择纳入日报也不产生 Work 或项目写入授权。已确认日报的修改仍按第一节处理。

### 只问实质问题

除上述内容候选外，默认不提问。仅在以下情况提问，涉及跟进的先通过第三节本人责任或关注准入：

- 两个可靠来源对最终事实直接冲突；
- 真实系统不可读取，且缺口会改变核心结论；
- 需要本人选择责任、范围、授权或外部状态；
- 证据表明某个先前决定被推翻，但会话里没有本人的理由或归因。问题写成「X 日定的 A 今天改成了 B，是判断错、前提变了还是对方信息错」，答案进所属主线或「想明白的」；
- DChat 群聊与项目清单出现稳定新增或冲突关系。确认前只保留为本次日报判断和 `unresolved`，不修改项目清单；私聊归属始终只用于本次日报，不持久化。

已有终态证据、三层准入的归属、是否算「想明白的」以及如何组织措辞由 Daily 自行判断；内容取舍仅在符合上述候选条件时交本人选择。问题必须带具体证据，并说明答案会改变哪项事实或动作；未解决的实质缺口才计入 `unresolved`。

### 每次交付的关联更新检查

生成或重做日报草稿、收到补录或纠正、本人确认日报时，均检查关联更新。检查范围是本次已核实的工作变化及其对应记录，包含因篇幅未进入日报正文的变化；复用本次证据与核对结果，只补查受影响部分。仅确认日报、没有新增事实时也执行检查；已有候选的依据与目标记录未变时复用结论。

收到补录时先区分结果发生时间与本次补录时间：补充的是截至目标日结束已经发生的结果，回到第三节更新对应核对记录及草稿；目标日之后新作出的决定留在之后的日报和当前更新候选中；发生时间不明且会改变日报事实时，按上节处理。已确认日报的重做仍按第一节执行。

按变化定位已有 Work 和项目入口，沿已有引用核对一跳。Work 按项目、目标、责任与完成条件匹配，必要时包含已完成记录，并用 `work show` 回读；项目只读对应正文。项目规则、配置和局部跟进各回到自己的主接收文档，影响项目范围、阶段、关键里程碑、责任或依赖的变化才提 CURRENT 更新。候选以目标记录的当前有效事实为准：已一致或已有更晚的有效事实时保持原样；发生冲突且无法判定时列具体缺口。确有差异时，在本次回复中一起列出具体候选，写清：

- 对应的 Work ID 或项目文档位置、现在怎么写、建议改成什么；
- 支持变化的本人原话或来源、实际发生时间，以及修改进展、完成、退出跟进等具体动作；
- 哪部分事实已经明确，哪部分还缺信息或需要本人选择。

没有对应记录时说明本次范围内无匹配；只有本人已认领、需独立跟踪的新结果才列新增候选；关注项形成具体动作且本人认领后再进入候选。候选保持为对话中的建议，不能代替本人授权。本人对具体候选的授权已明确时，Work 交顶层 Work 分支执行（新增走记录、已有记录走变更），项目更新按相应文档职责处理；日报确认、Work 写入和项目修改分别回读并报告。

交付时展开新增或发生变化的建议；本次已核对且无差异时说明“本次关联检查无需更新”；已有待选候选不变时只简述仍待选择，保留原候选入口。来源不可读时说明受影响对象与待补读内容，已读部分照常给结论。

完成标准：内容候选有具体事实、本人关系和取舍分歧，未选定的不进正文；其余问题命中事实、权限或外部状态门；本次工作变化对应的记录都有更新候选、保持原样的依据或具体覆盖缺口；生成、补录和确认三种触点均随本次回复交付检查结果，未授权候选保持未执行。

## 八、写入与确认

先按第三节核对记录逐项复核草稿，再使用 `lifeos reports write` 写入既有 draft，不直接编辑 `begin` 返回路径；正文文件只含 Markdown，frontmatter 由 CLI 拥有，字段与选项以 `--help` 为准。

日历已启用时，写入前必须在对话里列出「准备记入」和「剔除」两张会议清单（写法见 `calendar-evidence.md`），本人改完确认后才把记入的会写进「会议」一节；这一步不能省略，也不能用名单代替本人确认。`--calendar-scan-id` 传本次使用的 scan，`--calendar-event-id` 传窗口内全部日程的 `instance_id`（记入与剔除的都传，它们是审计信息）。

计数与 ID 的口径：`activity_ids` 是第二节那份完整 index 的去重 Activity ID，格式为 `ACT-` 加 24 位 Base32；`sessions_partial` / `sessions_interrupted` / `sessions_omitted` 同样只来自这一份 index，按 `session-evidence.md` 的定义取值；`work_event_ids`、`git_commit_ids` 和 `git_commits` 只记正文实际引用的对象。`git_commit_ids` 使用稳定的 `repo_key@完整 SHA`，不使用 LifeOS 另造的 per-commit ref；`project_key` 在 Git scan 时由当前 Project Catalog 即时解析，不复制进日报 ID。

本人明确确认后才运行 `lifeos reports confirm --day <YYYY-MM-DD>`，随后运行 `lifeos reports validate`，按第七节交付关联更新检查结果。

完成标准：第三节的逐项核对与正文对应检查通过，纯休假日报保留跨期承接路径；正文、计数和 ID 清单通过 validate；第七节的关联更新候选已随回复交付；没有本人确认时状态保持 draft。`reports validate` 证明报告结构与引用合法，逐项事实和责任的核对由本节写入前检查承担。

## 边界

Daily 分支不生成周期报或复盘，不写 Obsidian；周、月、季度、半年和年度总结转顶层 Periodic 分支。不关闭、改期或变更已有 Work 事实，也不替本人确认。Git 证据只读本地显式注册仓库，不上传、不访问 remote、不保存完整 diff、changed paths、author email 或未提交状态。DChat 只读结构化类型为 `p2p / extp2p` 的私聊和当前项目清单声明的群聊，不发送消息、不修改 DChat、不下载附件本体。日历只读日程的标题、起止时间、类型和参会人，不改日程、不回复邀请；会议是否参加只以本人确认为准，日历不能单独证明任何交付层级。
