# Daily 工作流

一天一份事实性日报，写进 Private Runtime，由本人确认。目标是恢复当天真实工作主线及其终态，不是逐条转述 Activity，也不要求每天都有价值、踩坑或经验。Git 提交和 DChat 是可选的辅助证据，不替代 Agent 会话、Work 或本人补录，也不能单独定义当天是否工作。读取来源证据不产生 Work 写入授权，确认日报也不等于确认 Work。

## 一、取得窗口

```bash
lifeos reports path --day <YYYY-MM-DD> --json
lifeos reports begin --day <YYYY-MM-DD> --json
```

目标日默认今天；日期边界只使用 `begin` 返回的 `window.from` / `window.to`。已确认日报保持不变；只有本人明确要求重做时才使用 `--redo`。

完成标准：目标状态和唯一自然日窗口已取得；重做时旧快照已由 CLI 留存。

## 二、盘点并审计证据

读取正文、判断 Activity、处理生命周期或填写 frontmatter 前，先读 `session-evidence.md`。运行 `lifeos dchat validate --json` 判断独立 DChat Evidence 是否已配置；配置有效时再读 `dchat-evidence.md` 并执行其中的采集门、渐进深读和项目确认规则。尚未配置只表示这一路尚未启用，不阻塞其他来源形成日报。

先确认目标窗口是否已经完成来源采集。`sessions index`、`list` 和 `pack` 只查询当前派生存储，不回读来源；结构完整的空 index 也不能证明窗口已经扫过。

```bash
lifeos sessions scans --from <window.from> --to <window.to> --json
lifeos sessions validate --scan <scan-id>
lifeos sessions scan --source all --from <window.from> --to <window.to> --json
lifeos sessions index --from <window.from> --to <window.to> --json
lifeos work changes --from <window.from> --to <window.to> --json
lifeos git scans --from <window.from> --to <window.to> --json
lifeos git scan --from <window.from> --to <window.to> --json
lifeos git validate --scan <git-scan-id> --json
lifeos dchat validate --json
lifeos dchat scans --from <window.from> --to <window.to> --json
lifeos dchat scan --from <window.from> --to <window.to> --json
lifeos dchat index --from <window.from> --to <window.to> --json
```

1. 先读 `sessions scans` 的精确窗口结果。只有记录的 `status=complete` 或 `status=partial`、`manifest_valid=true`、窗口完全相同，且 `codex`、`claude`、`smartwork`、`deepseek` 四个来源都存在且没有 `failed`，才算已有来源扫描；选中的记录还必须通过 `sessions validate --scan`。`partial` 表示本次扫描包含不完整 Slice 或来源警告，不等于没有采集结果；满足条件就复用，不重复扫描。
2. 没有可复用记录、来源缺失/failed 或校验失败时，执行一次目标窗口的 `sessions scan --source all`，随后校验新 `scan_id`。新扫描为 `partial` 时继续完整 index 和异常审计，并披露缺失边界；只有来源不可读、校验失败，或覆盖/异常不足以支撑结论时，才停止定稿并报告具体 Pending。不要把空 index 写成“昨日没有工作”。
3. 采集门通过后，读取无过滤的完整 index，必要时提高 `--max-bytes`，直到预算、丢弃项和保留期边界都明确。
4. 检查异常输入：同秒批量且切片很多、异常长或混合生命周期 Activity、partial 异常集中、疑似上下文导入。异常可能改变当天事实时，先展开定位；证据仍不可信则停止定稿并报告具体 pending。
5. 读取窗口内全部 Work changes。它们证明 LifeOS 账本发生了什么变化，不自动证明对应项目已经交付。
6. 如果有显式注册的 Git 仓库，先读目标窗口的 `git scans`。已有 `status=complete` 且通过 `git validate --scan` 的快照可以复用；没有快照、快照不完整或校验失败时，按需运行一次 `git scan`。Git scan 只读本地提交历史、写入私有证据快照，不修改仓库、不访问 remote、不写 Work。Git 不可用、没有注册仓库或扫描失败，不自动等于当天没有工作；只有当日报结论依赖 Git 且缺口影响事实时，才披露 pending 或提问。正文出现任何提交、推送、部署层级断言（含引用具体 commit 短 SHA）时，对应仓库窗口内必须有通过校验的快照，否则该断言降级为“会话陈述”。
7. 本人主动提供的补录作为第三路证据；没有实质缺口时不为了凑齐输入而提问。
8. DChat 已配置时，按 `dchat-evidence.md` 通过精确窗口 scan 和 validate 后读取完整 index；只对可能改变工作主线的会话渐进调用 pack。可读 scope 只采用 DChat 的结构化会话类型与关注 tag 判断，不按账号名称、头像或消息内容猜测身份，也不用群名、活跃度、本人是否发言或关键词扩大范围。

完成标准：来源采集门通过；全窗口覆盖可信；partial/中断/导入等所有可能改变自然日事实的异常已有解释或 pending；Work changes 已读取；Git 检查门已执行（目标窗口 `git scans` 已查询）；使用 Git 时选中 scan 已通过校验且仓库失败/缺失边界已解释；DChat 已配置时其精确窗口 scan、完整性和项目清单冲突已处理，未配置时没有把缺失解释成“没有聊天工作”。

## 三、建立工作主线

先选主线，再选需要深读的 Activity。Activity 是 evidence activity，不是任务、项目或日报章节；允许把多个来源、并行子 Agent 或多个 `project_key` 的 Activity 合并成同一工作主线，也允许把目标发生变化的长 Activity 拆成不同阶段。

工作主线以共同目标和可共享的总体终态为边界，不以项目名、仓库、对话或修改文件数机械分组。同一项目内目标和闭环状态彼此独立的工作可以拆成不同主线；不同项目只有在任务正文或交付证据明确表明它们共同服务于同一交付对象，且能够共享一个不冒充任一项目的总体终态时才合并。部门、主题、工具、群聊或名称相近不构成共同目标。

`project_key` 不能单独决定业务主题，但它与 `workspace`、`changed_targets` 共同形成项目边界证据。多个 Activity 指向不同项目根时，先分别判断各自的目标、交付物和终态；没有明确的跨项目交付证据就拆成不同主线。确需合并时使用中性的跨项目标题，并在正文中分别说明各项目贡献与边界，不能把其他项目的工作收进其中一个项目名下。DChat 会话候选只限定搜索范围，不能覆盖消息片段或已核验 Activity 的具体归属。

按以下信息判断重要性：

- 本人当天明确要推进的目标；
- 真实能力、交付状态或项目判断发生的变化；
- 反复纠偏、被推翻的判断或关键决策；
- 验证结果、实质风险、未闭环边界；
- 与当前项目主线的关系。

Activity 数量、持续时间、`signal_score` 和 `project_key` 只提供线索，不单独决定重要性和章节顺序。持续时间和投入强度可以提升叙事层级，但不能独自证明价值或完成；它们必须与当天目标、实质变化或终态证据一起判断。为每个高重要性 Activity 标记 `纳入某主线 / 并入其他 Activity / 次要概括 / 省略及理由`，避免重要活动静默消失。

为每条主线判断其变化结构，作为深读和表达选择，不作为正文固定标签：

- **简单变化**：围绕一个对象形成单一结果，没有影响终态的分支或转折；
- **多方向变化**：同一目标下有多个可分别说明的能力、规则、材料、运行或协调变化；
- **多轮变化**：同一方向经过验证、反馈或纠偏，后续判断实质替代了早期判断；
- **混合变化**：同时存在多个方向，且只有其中部分方向发生多轮变化。

只有变化会改变可用能力、项目判断、责任边界、交付状态、实质风险或下一步时，才把它作为独立方向。多个文件修改、参数调整、重复测试或普通措辞迭代不因此独立成项。

核心主线数量由当天事实决定，不设固定数量。当一项工作在重要性、可验证价值或实际投入上明显主导当天时，将它提升为唯一核心主线，其他事项降入“其他进展”；只有多项工作确实具有相近的叙事权重时，才并列为多条核心主线。没有足够重要的工作时也可以不设核心主线，不为版式凑数。

写初稿前做一次项目边界审计：为每条拟定主线回看其关键 Activity 的 `project_key`、`workspace`、`changed_targets` 与任务对象。标题含具体项目名时，纳入内容必须属于该项目，或有明确证据证明它是该项目交付的一部分；发现不同项目只有主题相近、却没有共同交付对象或共享终态时，立即拆分。

完成标准：当天所有高重要性 Activity 都有去向；并行分支已归并，混合目标已拆开；每条核心主线的变化结构已确定；项目边界审计没有发现被单一项目标题吞并的异项目工作；主线层级能反映当天真实重心，而不是 Activity 数量或预设章节数。

## 四、渐进深读与终态收敛

按主线分三级读取：

- **核心主线**：读取所有相关 Activity 的 `pack --activity`；对承载关键终态、验证或冲突的 Slice 再用 `sessions show` 回查。
- **次要进展**：读到能确定目标、动作、结果和边界即可。
- **琐碎活动**：使用 index 合并概括或省略，不为形式完整逐条展开。

每条核心主线先收敛最新结论，再按已确定的变化结构整理支撑它的内容。多方向变化按真实对象或结果归并，不给每个方向重复填写问题、纠偏、结果和边界；多轮变化只保留实质改变最终方案、完成状态、风险或下一步的关键转折，普通尝试和已被后续结果覆盖的中间状态压缩或省略。混合变化先分方向，只在发生关键转折的方向内展开演变，不把整条主线写成逐轮流水账。

需要保留多轮演变时，按 `最新结论 → 关键转折及原因 → 证明力最强的最新证据 → 剩余边界` 组织；没有纠偏时不补造转折。终态优先级取决于证据能证明什么，而不是哪句话最肯定。分别记录实现、本地测试、本地 Runtime、Git 提交、推送、部署和目标环境验证，前一层不能推出后一层。Git 提交只能证明对应仓库在该窗口产生了 commit 及其 commit message；不能据此推出测试通过、代码已推送、已部署或目标环境已验证。

证据和交付边界放在其真正适用的最小范围：整条主线共享时统一说明；只有某个变化方向的证据等级或完成层级不同，就紧跟该方向说明，不把局部证据扩大成整条主线的共同终态。

### 先定义这项工作

组织每条核心主线时，先用一到两句写出工作定义：这项工作在处理什么对象，做什么动作，想解决或确认什么，以及范围到哪里。工作定义是“事情本身”的入口，不要求绑定单一项目、仓库或 `project_key`；跨项目事项按实际对象合并，归属不清时以任务正文和目标对象为准。

标题和首段应让读者只看这两处就能复述工作范围。不要只写“文档同步”或“资源整理”这类工具标签；应具体到处理了哪类资料、进行了什么动作、形成了什么可判断结果。例子只用于说明具体性门槛，不是固定日报模板。

partial 和 `interrupted_with_result` 只在它们承载被引用事实或可能改变终态时深读；其可见结果和缺失边界必须按 `session-evidence.md` 披露。核心主线在不能说明以下内容时不得进入定稿：

- 为什么做；
- 做了哪些关键动作，判断如何变化；
- 最终结果是什么，由什么证据证明；
- 哪一层已经完成，哪一层仍未完成。

以上是主线级语义完整性检查，不要求每个变化方向分别具备一套固定字段。标题或上下文已经表达的信息无需重复；根据变化结构选择自然段、短列表、局部时间顺序或少量小标题。

完成标准：每条核心主线都有闭合的因果链和分层终态；多方向变化没有被挤进一个难以扫描的长段，多轮变化只保留影响最终判断的关键转折；中间观察没有覆盖后续已验证结论；引用到的不完整证据都有边界。

## 五、写自适应初稿

正文按当天重心和内容复杂度自适应组织，空章节省略：

```markdown
# 当日概览

用最短可扫描形式交代当天重心和总体状态；可以是一段话或少量要点，不重复后文。扫描计数、partial 数量等机械审计信息由 frontmatter 承担；只有证据缺口会影响正文结论时，才在概览或相关主线披露。

## <核心主线的自然语言标题>

先给出这条主线的当前结论，再按其变化结构说明主要变化和做到哪里。核心主线为一条时只保留这一条，为多条时按真实重要性排序。

## 其他进展

合并次要但值得保留的事项。

## 后续关注

只写已有证据支持、确实需要继续推进或等待的内容。

## 经验与问题

仅在形成可复用认识或真实踩坑时出现。
```

为每条主线选择能完整表达事实的最小形态：

- 简单变化使用一个短自然段；
- 多方向变化使用总体结论加按方向归并的短要点；
- 多轮变化先写最新结论，只在理解最终判断确有需要时补充少量关键转折；
- 混合变化先按方向拆分，只展开发生关键纠偏或存在独立风险的方向；方向本身足够复杂、具有独立终态时才使用局部小标题。

表达形态不要求固定栏目、固定要点数量或统一标签。不要给每个变化方向机械补齐“问题、纠偏、结果、边界”；共享信息在主线层只写一次，局部差异贴近对应方向。读者应先看到当前结论，再选择是否阅读变化过程。

价值是可使用或可验证的新能力、被消除的明确风险、得以推进的关键判断，或可复用且能降低未来成本的认识。修改动作本身不是价值。

踩坑是合理路径因隐藏约束失败、证据误导判断，或系统产生非预期行为，并经过定位形成了可复用的避免方式。普通修错、参数变化和未完成事项本身不是踩坑。

每条事实必须来自 Activity、Work event、Git commit evidence、DChat evidence 或本人补录；正文不写 ID。Git 的 `commit_message` 和 DChat 原文都是辅助线索，不能代替对实际工作结果的判断；没有 Git commit 或没有 DChat 消息也不能反推没有工作。不要为了固定篇幅制造价值、踩坑、经验或后续安排。

段落和列表各自只承载一个清晰语义；如果必须读完整个长段才能找到当前结论、各变化方向或完成边界，就按变化结构重新组织。不要用固定句数、字数或要点数量替代判断。

完成标准：主线数量、层级和顺序反映当天真实重心；读者不打开证据也能理解这项工作是什么、有哪些实质变化和做到哪；只看每条核心主线的标题和首段即可复述其对象、当前结论与范围；多方向和多轮主线无需通读长段即可找到变化与关键转折；不能复述时回查相关 Activity 的 `pack` / `show`，以实际对象补齐表述；可选分类和表达形式都由真实内容触发。

## 六、只问实质问题

默认不提问。仅在以下情况提问：

- 两个可靠来源对最终事实直接冲突；
- 真实系统不可读取，且缺口会改变核心结论；
- 需要本人选择责任、范围、授权或外部状态。
- DChat 群聊与项目清单出现稳定新增或冲突关系时需要本人确认；确认前只保留为本次日报判断和 `unresolved`，不修改项目清单。私聊归属始终只用于本次日报，不持久化。

已有终态证据、内容取舍、是否保留次要事项、是否叫“踩坑”以及如何组织措辞都由 Daily 自行判断。问题必须带具体证据，并说明答案会改变哪项事实或动作；未解决的实质缺口才计入 `unresolved`。

Daily 发现“后续要做”只决定日报如何表达。只有本人另外明确要求写入 LifeOS Work，才把原话和来源交给顶层 Work create-only 分支；Daily 不拼写 Work CLI，也不生成幂等键。

完成标准：每个问题都命中事实、权限或外部状态门；没有编辑性问题；未授权候选未进入 Work。

## 七、写入与确认

使用 `lifeos reports write` 写入既有 draft，不直接编辑 `begin` 返回路径。计数和 ID 只从同一份完整 index 取得：

```yaml
sessions_activities: <唯一 Activity 数>
sessions_partial: <partial Slice 数>
sessions_interrupted: <interrupted_with_result Slice 数>
sessions_omitted: <explicit_abort_without_work TurnOmission 数>
work_events: <引用事件数>
user_notes: <本人补录数>
unresolved: <实质未决数>
activity_ids: [<完整 index 的去重 ACT-...>]
work_event_ids: [<正文引用的 EVT-...>]
git_scan_id: <使用的 Git scan ID；未使用时留空>
git_commits: <正文引用的 Git commit 数>
git_commit_ids: [<正文引用的 repo_key@完整 SHA>]
```

`write` 负责机械闭合计数并原子写入。`git_commit_ids` 使用稳定的 `repo_key@完整 SHA`，不使用 LifeOS 另造的 per-commit ref；`project_key` 在 Git scan 时由已注册项目清单即时解析，不复制进日报 ID。本人明确确认后才运行 `lifeos reports confirm --day <YYYY-MM-DD>`，随后运行 `lifeos reports validate`。

完成标准：正文、计数和 ID 清单通过 validate；没有本人确认时状态保持 draft。

## 边界

日报不生成周报、月报或复盘，不写 Obsidian；不关闭、改期或变更已有 Work 事实，也不替本人确认。Git 证据只读本地显式注册仓库，不上传、不访问 remote、不保存完整 diff、changed paths、author email 或未提交状态。DChat 只读结构化类型为 `p2p / extp2p` 的私聊和带关注 tag 的群聊，不发送消息、不改标签、不下载附件本体；DChat 声称的完成或上线必须由更高等级证据核对。
