# Work 工作流

通过 `lifeos work` 读写 LifeOS 私有工作账本。项目正文和正式状态仍归对应 Project Workspace；项目名称、别名、scope、当前目录和核心 DChat/Cooper 入口来自动态 Project Catalog 中的 `lifeos-project.json`。Work 只保存按天记下的每一笔（待办、随记、疑问、洞见）、稳定 `project_key` 和个人项目跟踪状态，不复制项目静态内容、阶段或绝对路径。

## 授权门槛与分支

“事情要做”是日报或对话中的后续判断，不自动进入 Work。只有本人明确要求或确认写入 LifeOS Work 才进入记录分支；记成哪一种按 `work-model.md` 选择，只有真实歧义会改变结果时才询问。

- **读取：** 只执行读取命令，回答请求的范围、过滤条件、时间窗和空结果。
- **记录：** 先读必要事实，按 `work-model.md` 选记法并生成稳定幂等键，再 create-only 一次。
- **变更：** 只有明确的已有 ID 和当前意图才修改、完成、排到以后、划掉、转化、回答或改期；状态原因和完成信息按 `work-model.md` 处理。

日报候选、会话结论和“应该记下”的建议都先留在当前回答或日报里。本人另行确认“记个待办”“记一下”“这个问题先记着”“这条留下”或等价表达后，才进入 create-only，并逐条回收返回 ID。一次确认不扩成多笔；未提供的负责人、日期、星标和期限保持未知。

负责人为本人时不传 `--owner`；别人负责时只写已确认的真实名字，这条待办会进简报的「等别人」。字段缺失时不显示、不猜测。

## 项目关注联动候选

项目 CURRENT「当前推进」标题后缀 `（lifeos关注）` 表示本人要强关注该推进项。标记只圈定候选范围，两侧不存对方 ID；记法与状态按 `work-model.md`，现场判断与现有账本的关系。

**检出与匹配**：`rg -l "lifeos关注" --glob "CURRENT.md" <发现根>` 后只读命中项全文与必要直接来源；交接已提供原项与变化时使用该范围。通过 `lifeos work entries --project <project_key>` 检索相关待办与疑问，包括判断接续所需的已完成记录；按项目、目标、本人责任与完成条件匹配，正文仅辅助检索。当前简报不包含的记录需按需查询，不能从简报无记录推导账本无对应记录。

**触点**：日报确认时顺带盘点、本人按需要求、项目状态更新后的交接。已有 Work 巡检按其授权范围检查账本；此联动入口不新增调度器或后台扫描。

**记录与接续**：一个推进项可对应多条阶段待办；只记录本人已接下的执行责任，推进项的阶段与里程碑留在 CURRENT。已有待办能承接的优先更新；新阶段形成独立结果时，查重后提议新待办，保留已完成待办的历史。不因 CURRENT 有多步就一次建出整套未来待办；以后才做的用 `task-schedule` 排到对应月份，要不要做还没定的记成疑问。

**逐笔判断**：按每条待办自己的完成条件提议修改、完成、划掉或接续。阶段待办完成后继续核对推进项尚需完成的结果；推进项从 CURRENT 移除时核对实际完成、取消、替代或合并原因及残余责任，不据移除成批划掉账本记录。整个推进项完成的候选引用 WORKLOG 日期与标题；阶段待办完成引用直接支持其结果的证据，只存指针，不复制项目正文。

**确认与写入**：候选列明具体记录或拟新增结果、所属阶段、证据与动作，经本人对具体候选确认后执行；新增走 create-only，修改、完成、划掉等走相应变更分支。已匹配记录沿用原 ID 与来源身份；改名或同一待办进度变化沿用该身份。新记录与重试统一按 `work-model.md` 的稳定幂等规则；缺少不可变来源身份时先定位或确认，显示文字不能充当身份。写入后回读并验证。

**豁免**：未标记项不从此入口产生联动候选；取消关注只停止此入口的提议，不自动完成或划掉记录。已有账本记录仍受其本身的巡检和授权约束，与项目无关的个人记录不受标记限制。

## 读取分支

当前工作/待办查询采用 `lifeos work brief --mode current` 的用户易读结构：按重要紧急四组平铺自己的待办，再列等别人、没想通的和随记。
14:00 前瞻提醒直接使用 `lifeos work brief --mode current`；18:00 晚间收口使用
`lifeos work brief --mode closeout`；每月初的月初盘点使用 `lifeos work brief --mode monthly`，并按 `work-model.md` 的「月初盘点」逐笔问去向。它们都是确定性只读视图，Agent 直接转发 CLI
原生 Markdown，不再自行读取 JSON、重算日期、去重或重排。只有本人明确要求改变展示方式时，才转换格式。

查某个项目想明白过什么，用 `lifeos work entries --kind insight --project <项目> --live`；开始一个项目的工作前需要参考既往判断时也走这条。

1. 只读取请求需要的对象、时间窗、项目或状态；没有过滤时标明全量。
2. 分开报告来源事实、已确认变化和推导；说明空结果、无匹配和未覆盖范围。
3. 请求字段已完整回答后停止，不顺带创建或修订记录。

完成标准：请求范围和字段已回答，本分支没有 create、update、close 等写入动作。

## 写入分支

1. 回读目标记录及必要事实源，确认对象、当前状态和本人的明确授权。
2. 读取 `work-model.md` 中与该记法或状态相关的规则；正文收敛为一句话，日期、背景和步骤分别进截止时间、上下文或别的待办；缺少会改变结果的字段时询问，不补造。
3. 按稳定来源、对象类型和不可变来源身份生成或复用幂等键；相同请求重试复用同一键。
4. 执行一次对应 create 或明确授权的变更，回读对象和事件 ID。
5. 一批写入后运行一次 `lifeos work validate`，报告新增、变化、幂等处理、验证结果和待本人判断项。

完成标准：每个写入都有明确授权、稳定来源和稳定幂等键；验证通过；返回 ID 与实际变化可回读；候选和推导没有被写成账本记录。变更分支还要说明变更前后状态、本人给出的原因和对应历史事件。

## 交接与失败

Daily 交接候选时保留本人原话、事实来源、已确认字段和不可变来源身份。Work 返回记录或事件 ID 后，Daily 只保存该 ID 与结果摘要，不复制 Runtime 内容。

入口、Schema、Project Catalog、权限或验证失败时报告具体阶段和原始错误，保持账本不变；先按原幂等键回读，不通过换参数或换键把失败改写成已完成。发现单个跟踪项目暂时不可用时保留 `project_key` 和 Work 记录，只报告 linkage warning，不猜测路径或自动取消跟踪。Runtime 仍是 v1 结构时，先用 `lifeos work migrate-v2 --plan` 列出迁移清单交本人逐条决定，本人确认决定文件后才 `--apply`；不直接编辑 Runtime。
